Started 2026-07-19. User (Mayastor/SPDK engineer) wants to **integrate mTCP with SPDK** — repo `https://github.com/mtcp-stack/mtcp`. Read intent: make SPDK's NVMe/TCP data path run over mTCP's userspace TCP stack (kernel bypass), presumably to cut CPU-per-IOP in the [[project_mayastor_repos]] io-engine.

**Integration point (confirmed by architecture):** implement an mTCP-backed `spdk_sock` module — `struct spdk_net_impl` registered via `SPDK_SOCK_IMPL_REGISTER`, alongside SPDK's `posix`/`uring` impls. SPDK NVMe/TCP target (`lib/nvmf/tcp.c`) + initiator (`lib/nvme/nvme_tcp.c`) call through it. (SPDK C source is NOT vendored in the mayastor checkout — `spdk-rs/src/libspdk` only has `mod.rs` bindings; SPDK is built from nix.)

**Key findings from investigation:**
- **DPDK version chasm = the core blocker.** mTCP is pinned to DPDK ~17/18 (README still uses `setup_mtcp_dpdk_env.sh`, `x86_64-native-linuxapp-gcc` target, make-based `dpdk-setup.sh` menu — all gone after DPDK went meson at 19.11). mTCP unmaintained since ~2015 (last real release v2.0, Apr 2015). Mayastor SPDK = **v25.05-pre → DPDK ~24.x** (confirmed: running io-engine reports `SPDK v25.05.1-pre`; `spdk-rs/nix/pkgs/libspdk/default.nix` pins `version="25.05"`). Cannot co-init two DPDK EALs / two versions in one process.
- **Path that sidesteps the chasm (recommended for POC):** use mTCP's **netmap** backend (pluggable — mTCP supports DPDK/netmap/PSIO) so mTCP never calls `rte_eal_init`; SPDK keeps its DPDK 24 for storage, mTCP owns NIC via netmap, they coexist sharing hugepages. netmap **VALE switch / generic mode** allows testing with no dedicated NIC.
- **Threading mismatch (real, backend-independent):** mTCP spawns own per-core pthreads + own epoll (`mtcp_epoll_wait`); SPDK is reactor/poller based. sock impl must run mTCP context on the SPDK reactor thread and drive `mtcp_epoll_wait` from an SPDK poller.
- **Precedent:** SPDK once had a userspace-TCP sock impl (VPP) and **removed it (~20.x)** due to maintenance burden.

**DECISION (2026-07-19): F-Stack chosen over mTCP.** Deciding factor = DPDK version gap. F-Stack master is on **DPDK 22.11 LTS** (meson era, modern rte_flow/ethdev) → porting to SPDK's DPDK ~24.11 is 2 LTS steps, mechanical. mTCP is DPDK 18.11 (pre-meson) + dead since 2015. F-Stack also actively maintained (Tencent) + full FreeBSD TCP. Cost: F-Stack has **no netmap backend** (DPDK-only), so it forces the single-EAL problem head-on — no cheap POC sidestep like mTCP had. Clean part: F-Stack owns NIC+TCP, SPDK does NVMe framing over ffsock → zero NIC contention (SPDK NVMe/TCP only touches net via the sock layer). Integration surface confirmed: `struct spdk_net_impl` now lives in `include/spdk_internal/sock_module.h` (moved from sock.h); register via `SPDK_NET_IMPL_REGISTER_DEFAULT`. F-Stack epoll is in `lib/ff_epoll.h` (`ff_epoll_create/ctl/wait`, std sys/epoll.h layout) — clean map to SPDK's epoll-based sock_group.

**User picked scope = "feasibility spike first"** (not full embed, not io-engine yet). Smallest thing that proves control-loop inversion + one ff_socket round-trip through spdk_sock, before committing to the DPDK port.

**CRITICAL FIX for io-engine (non-obvious): `-Wl,-z,nostart-stop-gc`.** The io-engine is a `-pie` Rust binary linked with Rust's default `--gc-sections` + lld's default `-z start-stop-gc`. Diagnosed via gdb (pass RT signals SIG32-40 nostop, stop SIGSEGV) → fault_addr 0x48, %fs:(-0x5458)=curthread TLS. Fix in `/root/sandbox/mayastor/.cargo/config.toml` rustflags: add `-C link-arg=-Wl,-z,nostart-stop-gc` (retains start/stop-referenced sections = the SYSINIT set, while still gc'ing genuinely-unused code; a blanket `--no-gc-sections` instead pulls in unresolved isal-crypto AVX variants — DON'T use it). nvmf_tgt (SPDK's own build, no gc-sections) never hit this.
